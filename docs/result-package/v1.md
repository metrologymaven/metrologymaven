# Metrology Maven Result Package, format version 1

- **Format name:** `metrologymaven-result-package`
- **Format version described:** `1.0.0` (readers of major version 1 accept every `1.x.y`)
- **Status:** draft for the first public release. The predicate type URIs are internal working names until the project name is final (D-002).
- **Licence:** this text is published under the Creative Commons Attribution 4.0 International licence (CC-BY-4.0). The JSON Schemas and conformance fixtures it names are project data under the same licence.
- **Spec nodes:** TRUST.PKG (format), TRUST.PKG.MANIFEST (layout, manifest, statement), TRUST.PKG.READER (limits and fail-closed reading), TRUST.PKG.FIXTURE (this text and the conformance set).

This document is original project text. It cites outside specifications by name and section only and copies none of their text.

## 1. Purpose

A Result Package carries exported measurement results together with the evidence needed to check them: the ResultRecords, the journal segment that produced them, the kernel manifest, the active profile and, optionally, the input point sets. Anyone who holds only the package and a conforming reader can check that every member is the one the package states, and a signature checker can check who stated it. A replaying verifier can recompute the results from the included points.

Key words: **must** and **must not** are requirements on writers and readers; **should** is a recommendation.

## 2. Container

A package is a ZIP archive as described by PKWARE's APPNOTE, with the zip64 extensions when a size, offset or count needs them. To make the bytes a function of the contents only, a writer must produce:

- entries in this order: `manifest.json`; then every member, sorted by the UTF-8 bytes of its path; then `statement.json`; then, if the package is signed, the entries under `signatures/` sorted by name;
- for every entry: modification time and date 1980-01-01 00:00:00, general-purpose flag bit 11 (UTF-8 name) and no other flag, no data descriptor, no encryption, no entry comment, no extra field other than the zip64 one, "version made by" Unix 4.5, external attributes of a regular file with mode 0644;
- compression chosen from the media type alone: method 0 (stored) for already compressed media (`application/gzip`, `application/x-bzip2`, `application/x-xz`, `application/zip`, `application/zstd`, `image/jpeg`, `image/png`), method 8 (deflate) for every other type. The reference writers use a deflate stream made of stored blocks only, so the output does not depend on a compressor's version;
- a single end of central directory record at the very end of the file, no archive comment, one disk.

A reader must not depend on the deflate encoding a writer chose, only on the inflated bytes.

## 3. Members

Every member path is relative, uses `/` as separator, is Unicode NFC, is at most 4096 UTF-8 bytes, and has no empty, `.` or `..` segment, no backslash, no NUL and no drive prefix. Its first segment must be one of the reserved folders below. Two paths must not be equal after full Unicode case folding, and no path may also be the folder of another.

<!-- members -->
| Member | Media type | Content |
|---|---|---|
| `manifest.json` | `application/json` | The manifest (section 4). Always the first entry. |
| `results/records.json` | `application/json` | RFC 8785 JSON array of ResultRecords, sorted by `id` bytes (section 6). |
| `results/results.qif` | `application/xml` | The same results as a QIF Results document. Its content is defined by IO.RES.QIFR.ROUT; the golden packages hold a labelled placeholder. |
| `journal/segment.jsonl` | `application/x-ndjson` | The journal segment that produced the results, one RFC 8785 entry per line (section 7). |
| `journal/checkpoints/<index>.json` | `application/json` | Each checkpoint that anchors the segment, in the journal's checkpoint canonical form. |
| `points/<sha256>.<ext>` | by format | One input point set per distinct digest, named by the lowercase hex SHA-256 of its bytes. Present only at evidence tier `points`. |
| `kernel/manifest.json` | `application/json` | The kernel manifest (schemas/kernel-manifest.schema.json) whose SHA-256 is `kernel_manifest_digest`. |
| `profile/profile.json` | `application/json` | The active profile document whose SHA-256 is `profile_digest`. |
| `statement.json` | `application/json` | The in-toto Statement (section 5). Always after the members. Not listed in the manifest. |
| `signatures/<n>.dsse.json` | `application/json` | DSSE envelopes added after export (section 8). Not listed in the manifest. |
<!-- /members -->

A package must contain no other entry: a reader rejects any entry that is neither listed in the manifest nor `statement.json` nor under `signatures/`.

## 4. Manifest

`manifest.json` is RFC 8785 canonical JSON with no trailing newline. JSON Schema: [`schema/manifest-1.json`](../../schema/manifest-1.json). Numbers are written as decimal strings, so the document holds only strings, arrays and objects.

<!-- fields manifest -->
| Field | Type | Meaning |
|---|---|---|
| `format` | string | Always `metrologymaven-result-package`. |
| `format_version` | string | Semantic version `MAJOR.MINOR.PATCH`. A reader of major N accepts any minor version of N and ignores fields it does not know; it rejects another major version. |
| `created_by` | string | Free text naming the writer. Not interpreted. |
| `evidence_tier` | string | `results`, `features` or `points`: how much evidence the package carries (section 6). |
| `profile_digest` | string | `sha256:` + 64 hex digits of `profile/profile.json`. |
| `kernel_manifest_digest` | string | `sha256:` + 64 hex digits of `kernel/manifest.json`. |
| `members` | array | One object per member except `statement.json` and `signatures/*`, sorted by path bytes. |
| `path` | string | Member path (section 3). |
| `media_type` | string | Lowercase `type/subtype`, at most 255 bytes. |
| `length` | string | Byte length of the inflated member, decimal, no leading zeros. |
| `sha256` | string | Lowercase hex SHA-256 of the inflated member. |
<!-- /fields -->

## 5. Statement

`statement.json` is an in-toto Statement v1 (in-toto attestation framework, Statement layer), RFC 8785 canonical, no trailing newline. JSON Schema: [`schema/statement-1.json`](../../schema/statement-1.json).

<!-- fields statement -->
| Field | Type | Meaning |
|---|---|---|
| `_type` | string | `https://in-toto.io/Statement/v1`. |
| `subject` | array | `manifest.json` first, then every manifest member in manifest order. |
| `name` | string | The subject's member path. |
| `digest` | object | Holds only `sha256`, lowercase hex. |
| `predicateType` | string | `https://metrologymaven.io/result-package/predicate/v1` (working name). |
| `predicate` | object | The package predicate below. |
| `manifest_sha256` | string | Lowercase hex SHA-256 of the `manifest.json` bytes. |
| `format_version` | string | Equal to the manifest's `format_version`. |
| `result_count` | string | Number of ResultRecords, decimal. |
| `evidence_tier` | string | Equal to the manifest's `evidence_tier`. |
<!-- /fields -->

## 6. Results and evidence tiers

Each ResultRecord carries at least the fields of CONSTITUTION section 5: `id`, `characteristic`, `measurand`, `evaluation_basis` (`POINTS`, `FEATURES`, `RESULTS_ONLY` or `DIRECT_READING`), `value` (`value` as binary64 bits in `0x` hex, and `unit`), `uncertainty` (with `class` UEC-0 to UEC-3), `decision` (`rule` and `outcome`: `CONFORMS`, `NONCONFORMS`, `INDETERMINATE` or `NOT_DECIDABLE`), `spec` (standards with edition, and the defaults profile), `algorithm` (ID with version), `kernel_version`, `input_digests` and `journal_entry` (the hash of the journal entry that produced it). Readers ignore fields they do not know.

A result whose uncertainty class is UEC-0 has not been evaluated. Its `uncertainty` is exactly `{"class":"UEC-0","status":"not_evaluated"}`: it has no numeric field, and a writer must never put a substitute value there.

The evidence tier says what the package carries:

- `results`: records, journal segment, kernel manifest and profile; no point sets. A verifier can check integrity and signatures but cannot recompute any result.
- `features`: as `results`; results computed from features can be traced through the journal, but no point set is included.
- `points`: as `results`, plus every point set named by the included records' `input_digests`.

## 7. Journal segment

`journal/segment.jsonl` holds one line per journal entry, each line `{"header": ..., "payload": ...}` in RFC 8785 form followed by one LF. The header is the entry header of the project journal (schema/entry.schema.json); its `hash` is the SHA-256 of the canonical header without `hash`, and its `prev` is the previous entry's hash. The payload carries the detachable fields (salts, arguments, events) and may be absent when it was redacted; the salted commitments in the header stay, so the hash chain still checks. The segment starts at the latest checkpoint at or before the earliest referenced entry, or at the session header if there is none, and ends at the latest entry a record references.

## 8. Signatures

A package is signed by adding DSSE v1 envelopes (Dead Simple Signing Envelope, version 1) under `signatures/`, after `statement.json`. The payload type is `application/vnd.in-toto+json`. An envelope's payload is either the `statement.json` bytes themselves, or a signature statement: an in-toto Statement v1 whose single subject is named `statement.json` and carries its SHA-256, with predicate type `https://metrologymaven.io/signature/predicate/v1` (working name, owned by TRUST.ESIG.BIND) and a predicate stating the signer-asserted `signed_at`, `meaning_code` and `key_fingerprint`. Signatures do not change the manifest or the statement, so adding one never changes a member digest. Key fingerprints are the lowercase hex SHA-256 of the key's SubjectPublicKeyInfo DER. Trust in a key comes from an offline trust root (TRUST.SIGN.TROOT), never from the package.

## 9. Limits

A conforming reader must reject, with a typed error and without crashing, any package that exceeds these limits, checking each from the declared values before it reads the bytes or reserves the memory they would need:

- total package size 16 GiB;
- 1,000,000 entries;
- 4096 bytes per entry name;
- `manifest.json` at most 64 KiB plus 4608 bytes per entry, and never more than 256 MiB (the reference reader caps it at 16 MiB);
- a decompression ratio of 1000:1, declared and while streaming, and no member inflating past its manifest length.

## 10. Error codes

A conforming reader reports one of the codes below. The reason tag narrows the code; reasons are stable, and a verifier may compare them.

### `pkg.limit`

A published limit (section 9) was exceeded.

<!-- reasons pkg.limit -->
| Reason | When |
|---|---|
| `package_size` | The file is larger than 16 GiB. |
| `member_count` | More than 1,000,000 entries are declared. |
| `path_length` | An entry name is longer than 4096 bytes. |
| `manifest_size` | `manifest.json` is larger than its size limit. |
| `manifest_budget` | `manifest.json` holds more JSON values than its element budget for the entry count. |
| `member_length` | A member inflates past its declared or manifest length. |
| `ratio` | A member's declared or streamed decompression ratio exceeds 1000:1. |
| `index_budget` | The parsed central directory would need more memory than the reader allows. |
| `buffer_cap` | A member is larger than the caller's buffer cap. |
<!-- /reasons -->

### `pkg.unlisted_member`

An entry is neither listed in the manifest nor `statement.json` nor under `signatures/`.

### `pkg.unsupported_version`

The manifest's format major version is not one the reader supports.

### `pkg.bad_path`

A writer was given a member path that breaks the rules of section 3.

### `pkg.duplicate_path`

A writer was given two members with the same path, or paths equal after case folding.

### `pkg.schema_invalid`

A writer was given contents that do not fit the manifest or statement schema.

### `pkg.io`

Reading or writing the package failed for a reason other than the end of the file.

## 11. Conformance

The conformance set lives in `fixtures/pkg/` and is rebuilt byte for byte by `python fixtures/pkg/generate`; `--check` fails, naming each fixture, when a committed file differs from its regenerated form.

- `golden/index.json` lists the golden packages with their pinned SHA-256, evidence tier, record IDs, UEC-0 record IDs and signatures. There is one package per evidence tier (`results.zip`, `features.zip`, `points.zip`), one with two signatures (`two-signatures.zip`, signed with the published RFC 8032 and RFC 6979 test keys in `fixtures/dsse/keys`; these keys prove nothing) and one with a UEC-0 result (`uec0.zip`). A conforming reader must accept every one.
- `malformed/<case>/package.zip` with `expect.json` (`error_code`, `reason`, `note`): one case per failure class. A conforming reader must reject each with the expected `error_code`; a reader that also reports reasons should report the expected `reason`. `pkg.io`, `source_changed`, `package_size`, `index_budget` and `buffer_cap` cannot be expressed as a static file and are tested in the reference reader's own suite.
- `python fixtures/pkg/run-conformance [--reasons] -- READER [ARG ...]` runs any reader over the set. The reader is called as `READER ARG ... <package>` and prints one JSON object: `{"result":"accepted"}` or `{"result":"rejected","error_code":"...","reason":"..."}`. The reference reader is the `fid-pkg-conformance` binary of the `fid-pkg` crate.

Everything in the conformance set is synthetic and generated by the project; it contains no third-party data.
