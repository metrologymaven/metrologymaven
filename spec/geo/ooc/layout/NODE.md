# GEO.OOC.LAYOUT: Chunk layout, manifest and conversion

## Purpose

Defines how a very large point cloud is cut into spatial chunks and stored: an octree partition, a versioned chunk byte format stored as content-addressed blobs in CORE.STO, a manifest that names the whole chunked cloud, and conversion in both directions, including a streaming writer that IO uses to build chunks from files larger than memory.

## Scope

**In:**
- Octree partition of the cloud's AABB; a cell is split when it would hold more than `max_chunk_points` (default 2²⁰)
- Chunk format v1: header (`FIDCHK`, version, cell code, count, channel list), then columns: original point index (u64), x, y, z (f64), then attribute channels, all little-endian
- `ChunkManifest`: frame, AABB, octree parameters, chunks in Morton order with counts and blob digests, the original element digest, and the manifest digest
- `to_chunks(&PointCloud)` and `to_memory(&ChunkManifest)` (with a memory check)
- `ChunkWriter`: streaming builder fed in original order, with a bounded spill buffer, computing the original element digest on the fly

**Out:**
- Caching and loading with integrity checks (owned by `GEO.OOC.CACHE`)
- Iteration order (owned by `GEO.OOC.STREAM`)
- File formats such as LAS, LAZ, COPC and E57 (owned by `IO`); IO feeds `ChunkWriter`
- Blob storage itself (owned by `CORE.STO`)

## Requirements

- **REQ-GEO.OOC.LAYOUT-001** Each chunk shall store the original point index of every point, so the original order can be reconstructed.
- **REQ-GEO.OOC.LAYOUT-002** Converting an in-memory cloud to chunks and back shall reproduce the original element digest exactly.
- **REQ-GEO.OOC.LAYOUT-003** The manifest digest shall depend only on the frame, octree parameters and chunk contents, so the same cloud chunked twice gives the same manifest digest.
- **REQ-GEO.OOC.LAYOUT-004** `ChunkWriter` shall build a chunked cloud of 10⁹ points while its own resident memory stays below a configured spill budget (default 1 GiB [unverified]).
- **REQ-GEO.OOC.LAYOUT-005** If `to_memory` would need more memory than a given budget, then it shall fail with `BudgetExceeded { needed }` before allocating.
- **REQ-GEO.OOC.LAYOUT-006** The chunk format shall carry a version byte, and a reader shall reject an unknown version with `UnsupportedChunkVersion`.

## Acceptance criteria

- **AC-1** Given fixture `fixtures/geo/ooc/cloud_5e6` (5 × 10⁶ points with normals and intensity, seed 61), when converted to chunks with `max_chunk_points = 65 536` and back, then the element digest equals the original.
- **AC-2** Given the same cloud chunked twice (once in memory, once through `ChunkWriter`), then both manifest digests are equal.
- **AC-3** Given a seeded generator of 10⁹ points streamed into `ChunkWriter` with a 1 GiB spill budget, when run on CI's large runner, then the counting allocator reports peak writer memory below 1 GiB and the manifest lists 10⁹ points [unverified runner].
- **AC-4** (error path) Given `to_memory` with a budget smaller than the cloud, then it fails with `BudgetExceeded` and allocates nothing.
- **AC-5** (error path) Given a chunk blob with version byte 9, when read, then `UnsupportedChunkVersion` is returned.

## Design

- **Registry command(s):** none; library leaf (commands in GEO.OOC.CMD).
- **Data structures:** `CellCode(u64)` (depth plus Morton code); `ChunkHeader`; `ChunkManifest { frame, aabb, max_chunk_points, chunks: Vec<ChunkEntry { cell, count, blob: [u8; 32] }>, original_digest, manifest_digest }`; `ChunkWriter`.
- **Algorithm:** the writer needs the cloud AABB up front (from the file header or a first pass by IO); points are bucketed into a fixed-depth grid in spill files, then over-full buckets are split recursively; within a chunk points are ordered by original index.
- **Errors:** `BudgetExceeded`, `UnsupportedChunkVersion`, `CorruptChunk`, store errors from CORE.STO.
- **Determinism:** D0 for layout and digests.
- **Performance budget:** chunking 10⁸ points under 60 s on reference hardware [unverified].
- **Crate:** `fid-geo-ooc` (outside the kernel graph because it does storage I/O; kernel code receives points through the GEO.OOC.STREAM trait).

## Open questions

- The parent asked whether chunks should follow COPC so IO can memory-map files directly. This leaf keeps an own format inside the CORE store, so GEO does not depend on a file format IO owns; IO converts COPC into chunks through `ChunkWriter`. If import time for COPC proves too high, a COPC-backed chunk source can be added later behind the same manifest.
