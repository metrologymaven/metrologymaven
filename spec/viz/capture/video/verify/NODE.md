# VIZ.CAPTURE.VIDEO.VERIFY: Recorded media verification against journal digests

## Purpose

Checks every segment attached to a recording (video and view track) against the digests in its attach entries and reports each one `ok`, `tampered` or `missing`, after first checking the journal chain those entries sit in. The function is also exported for package-level verification.

## Scope

**In:** `capture.verify_media@1` (R0); the library function `verify_recording(journal, store, recording_id)`; segment and manifest digest checks; sequence-gap detection.
**Out:** chain verification itself (`CORE.JRN.CHAIN.VERIFY`); package verification reports (`TRUST.VERIFY`); attaching segments (`VIZ.CAPTURE.VIDEO.PIPE`, `VIZ.CAPTURE.TRACK.SAMPLE`).

## Requirements

- **REQ-VIZ.CAPTURE.VIDEO.VERIFY-001** For each `capture.attach_segment@1` and `capture.attach_track_segment@1` entry of the recording, the command shall report `ok` when the stored segment and manifest hash to the entry's digests, `tampered` when either is present but hashes differently, and `missing` when either is absent.
- **REQ-VIZ.CAPTURE.VIDEO.VERIFY-002** If the journal chain containing the attach entries does not verify, then the command shall report `chain_invalid` and no per-segment `ok`.
- **REQ-VIZ.CAPTURE.VIDEO.VERIFY-003** The command shall report a gap for every missing sequence number between 0 and the highest attached sequence number of each source.
- **REQ-VIZ.CAPTURE.VIDEO.VERIFY-004** The result shall be ordered by source, then sequence number, and identical inputs shall give byte-identical canonical output.

## Acceptance criteria

- **AC-1** Given fixture `fixtures/viz/capture/recording-3seg` (a journal and store with three video and three track segments), when `fid capture verify-media --recording <id> --json` runs, then all six report `ok`.
- **AC-2** (error path) Given one byte flipped in video segment 1 on disk, then segment 1 reports `tampered` and the others `ok`.
- **AC-3** Given video segment 2 deleted from the store, then it reports `missing`; given the attach entry for seq 1 removed from a test journal copy, then the chain check fails and the result is `chain_invalid`.
- **AC-4** Given the same store twice, then outputs are byte-identical.

## Design

- **Registry command(s):** `capture.verify_media@1`, R0; params `{ recording_id }`; result `{ chain: ok|chain_invalid, segments: [{ source, seq, segment: ok|tampered|missing, manifest: ok|tampered|missing }], gaps: [{ source, seq }] }`.
- **Algorithm:** verify the chain range from the recording's start entry to its stop entry; collect attach entries; read blobs with integrity checking disabled-to-report (an `integrity` error from CAS maps to `tampered`, not-found to `missing`).
- **Errors:** `UnknownRecording`.
- **Determinism:** D0.
- **Performance budget:** dominated by hashing; 1 GB of media < 5 s on the reference profile [unverified].
- **Crate:** `fid-capture` (module `verify`).
