# RPT.CATALOG.QUERY.EXEC: Typed catalog query, ordering and pagination

## Purpose

Answers `stats.query_results@1`: a typed `CatalogQuery` (filters, sort keys, page size, cursor) is translated into parameterised SQL over one catalog, returning entries in a total, deterministic order with a stable cursor. No user text ever becomes SQL. It also exposes a per-catalog executor that `RPT.CATALOG.SHARE.FED` merges across attached catalogs.

## Scope

**In:** `CatalogQuery` type; filters (part, revision, characteristic, time window, tag, stage, decision outcome, evaluation basis, record status, entry status); sort keys; keyset cursor; page size 1–10 000 (default 500); translation to SQL with bound parameters; the benchmark.

**Out:** saved queries (`RPT.CATALOG.QUERY.SAVE`); queries spanning several catalogs (`RPT.CATALOG.SHARE.FED`); exclusion of `STALE` entries from statistics (`RPT.STATS.DSET`).

## Requirements

- **REQ-RPT.CATALOG.QUERY.EXEC-001** `stats.query_results@1` shall be R0 and accept only a typed `CatalogQuery`; an unknown field shall fail with error `stats.query_invalid`.
- **REQ-RPT.CATALOG.QUERY.EXEC-002** Every filter value shall be passed to SQLite as a bound parameter, and the SQL text shall be built only from fixed fragments chosen by the query's enum fields.
- **REQ-RPT.CATALOG.QUERY.EXEC-003** Results shall be ordered by the requested sort keys followed by record ID, defaulting to part, characteristic, timestamp, record ID.
- **REQ-RPT.CATALOG.QUERY.EXEC-004** Pagination shall use a keyset cursor over the full sort tuple, so that paging through an unchanged catalog returns every match exactly once.
- **REQ-RPT.CATALOG.QUERY.EXEC-005** A query filtered by part and characteristic over 1 000 000 entries shall return its first page of 500 in under 1 s on reference hardware [unverified].
- **REQ-RPT.CATALOG.QUERY.EXEC-006** If a cursor was issued for a different query, then the command shall fail with error `stats.cursor_mismatch`.

## Acceptance criteria

- **AC-1** Given fixture `fixtures/rpt/catalog/query_10k` (10 000 synthetic entries), when `fid stats query-results --part P1 --char C3 --json` runs, then all matching entries are returned in (part, characteristic, timestamp, record ID) order.
- **AC-2** When the same query is paged with page size 7, then the concatenated pages equal the unpaged result exactly.
- **AC-3** (injection) Given a characteristic filter value `x' OR 1=1 --`, then zero rows are returned and the SQL text logged by the test hook contains no part of the value.
- **AC-4** (error path) Given a cursor from another query, then `stats.cursor_mismatch`; given an unknown field, `stats.query_invalid`.
- **AC-5** (benchmark) Given the generated 1 000 000-entry catalog `query_1m` (seed 42), the first page returns in under 1 s on the reference machine [unverified until measured].

## Design

- **Registry command:** `stats.query_results@1(query: CatalogQuery) -> { entries: Vec<CatalogEntry>, next: Option<Cursor> }` (R0, `--json`).
- **Data structures:** `CatalogQuery { filters: Filters, sort: Vec<SortKey>, page_size: u32, cursor: Option<Cursor> }`; `Cursor` = query digest plus last sort tuple, encoded as canonical JSON then base64.
- **API for federation:** `fn execute(catalog: &Catalog, q: &CatalogQuery) -> Result<Page, QueryError>` and `fn sort_tuple(entry, sort) -> SortTuple`.
- **Errors:** `stats.query_invalid { field }`, `stats.cursor_mismatch`, `stats.catalog_unavailable`.
- **Determinism:** D0; total order on every result.
- **Performance budget:** as REQ-005.
- **Crate:** `fid-catalog` (module `query`).
