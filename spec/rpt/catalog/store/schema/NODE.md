# RPT.CATALOG.STORE.SCHEMA: Catalog database schema and migrations

## Purpose

The catalog is a local SQLite file, separate from every project database, that indexes ResultRecord summaries across registered projects. This task leaf defines its tables, indexes, schema versioning and forward migrations, and the open function that finds the catalog at the location set in user settings. It stores values (with digests), not only references, so that queries over a million results stay fast; every row still points back to its source project, record and journal entry hash.

## Scope

**In:**
- Tables: `catalog_meta` (schema version, catalog ID, owner), `project` (project ID, handle, last indexed journal position and head hash, availability), `entry` (one row per ResultRecord), `entry_tag`
- `entry` columns: project ID, record ID, part, revision, plan, run, stage, characteristic, timestamp, value literal and unit, SI value, decision outcome, rule ID, evaluation basis, UEC class, record status (`active`, `voided`, `superseded`), source journal entry hash, entry status (`ok`, `unverified`, `stale`, `unavailable`)
- Indexes for (part, characteristic, timestamp, record ID) and (project, journal position)
- Schema version check and forward-only migrations in one transaction
- Catalog location as a user-scope setting `stats.catalog_path` with a default in the per-user data directory

**Out** (and which node owns it instead):
- Registration commands (`RPT.CATALOG.STORE.REG`) and indexing (`RPT.CATALOG.STORE.INDEX`)
- Query translation (`RPT.CATALOG.QUERY.EXEC`); integrity statuses computed by `RPT.CATALOG.CHECK`
- Project databases (`CORE.STO.SQL`)

## Requirements

- **REQ-RPT.CATALOG.STORE.SCHEMA-001** The `entry` table shall have a unique key (project ID, record ID) and shall store the source journal entry hash for every row.
- **REQ-RPT.CATALOG.STORE.SCHEMA-002** When the catalog is opened with an older schema version, the system shall apply every forward migration in one transaction, and if the file has a newer version than the build supports, then opening shall fail with error `stats.catalog_too_new` without modifying the file.
- **REQ-RPT.CATALOG.STORE.SCHEMA-003** All text columns that come from project content shall be stored as data and read back as untrusted text (CONSTITUTION C6).
- **REQ-RPT.CATALOG.STORE.SCHEMA-004** Opening the catalog shall need no network service and no account (CONSTITUTION C7).
- **REQ-RPT.CATALOG.STORE.SCHEMA-005** If the catalog file is missing, then opening it for writing shall create an empty catalog at the configured location with a new UUIDv7 catalog ID.

## Acceptance criteria

- **AC-1** Given no catalog file, when the catalog is opened for writing in a test with a temporary settings scope, then an empty catalog with the current schema version and a catalog ID is created.
- **AC-2** Given fixture `fixtures/rpt/catalog/schema_v1.sqlite`, when opened by a build with schema v2, then the migration runs once, the version reads 2 and every v1 row is present.
- **AC-3** (error path) Given a catalog whose version is newer than the build, then opening fails with `stats.catalog_too_new` and the file digest is unchanged.
- **AC-4** Inserting two rows with the same (project ID, record ID) fails with a constraint error.
- **AC-5** With networking disabled in the test sandbox, AC-1 to AC-4 pass.

## Design

- **Registry commands:** none (library).
- **API:** `Catalog::open(path, mode: ReadOnly | ReadWrite) -> Result<Catalog, CatalogError>`; `Catalog::schema_version()`; migration list as ordered SQL scripts embedded in the crate.
- **Data structures:** `CatalogEntryRow` mirroring the columns above; `EntryStatus`, `RecordStatus` enums stored as fixed strings.
- **Errors:** `stats.catalog_too_new`, `stats.catalog_corrupt`, `stats.catalog_locked`.
- **Determinism:** D0; schema and migrations are fixed text.
- **Performance budget:** open and version check under 20 ms [unverified until measured].
- **Crate:** `fid-catalog` (module `schema`, location setting in module `location`), using `rusqlite` with the pin and features of D-043 (D-047) and `fid-store`'s shared SQLite hardening and migration runner (#405).

## Open questions

- Resolved from the parent: the catalog stores values with digests, not only references.
- Built (2026-11-21): schema v1 is `catalog_meta`, `project`, `entry` and the (part, characteristic, timestamp, record ID) index; v2 adds `entry_tag` and the (project, journal position) index, so AC-2 has a real migration. `entry` also stores `journal_seq` (the journal position the second index needs) and the D-045 evidence labels `claimed`, `declared_input`, `uncharacterized_input` and `interpretation`, with no defaults; table checks (re-checked on read) refuse a claimed value that is not UEC-1, a UEC-1 entry that does not have exactly one of `claimed` and `uncharacterized_input` (UNC.UEC.CLASS: a declared input alone does not make a value UEC-1), a UEC-2 or UEC-3 entry with a declared or uncharacterized input, and a UEC-0 entry with a value or any label. A write open runs `PRAGMA quick_check` before it sets WAL mode, and again under the migration's write transaction when an existing catalog is migrated. Connections come only from `fid-store`'s guarded `open_hardened` (D-047).
- Built: extra error codes `stats.catalog_read_only` (a read-only open of an older schema, or a write on a read-only open), `stats.catalog_missing`, `stats.catalog_path_invalid`, `stats.catalog_migration_failed`, `stats.catalog_constraint` and `stats.catalog_io`. `stats.catalog_path` holds an absolute path, or `""` for `<per-user data directory>/fiducial/catalog/catalog.sqlite`.
- Built: the `catalog_meta` owner is an optional label given at creation; who the owner is (a principal, a machine) is for `RPT.CATALOG.SHARE` to settle.
