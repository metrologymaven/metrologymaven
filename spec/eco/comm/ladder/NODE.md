# ECO.COMM.LADDER: Maintainer-eligibility report

## Purpose

Computes, per domain, which contributors meet the GOVERNANCE.md nomination thresholds (5 merged node expansions, or 3 expansions plus 5 substantive reviews, and no reverted splits in the last 60 days), so the contributor ladder runs from data rather than memory. The report informs nominations; it never nominates anyone.

## Scope

**In:**
- Counting merged expansions per author and domain from commit history (`spec(<ID>): split|leaf|blocked on`)
- Counting substantive reviews from a review export
- Detecting reverted splits within the window
- A Markdown and JSON report, marked generated

**Out:**
- Nominations and their lazy-consensus period (people, per GOVERNANCE.md)
- Maintainer lists in `owners:` (edited by maintainers)

## Requirements

- **REQ-ECO.COMM.LADDER-001** The report shall attribute a merged expansion to the domain given by the first segment of the node ID in the commit subject, and to the commit's author.
- **REQ-ECO.COMM.LADDER-002** A review shall count as substantive when its state is "approved" or "changes requested" and it has a non-empty body or at least one inline comment, unless the config overrides the rule.
- **REQ-ECO.COMM.LADDER-003** A contributor shall be listed as eligible in a domain when (expansions ≥ 5, or expansions ≥ 3 and substantive reviews ≥ 5) and no split of theirs in that domain was reverted in the 60 days before `--now`, with all thresholds read from config.
- **REQ-ECO.COMM.LADDER-004** The report shall list, for each eligible contributor, the counts and the commit and review references they are based on.
- **REQ-ECO.COMM.LADDER-005** Given the same history, review export, config and `--now`, the report shall be byte-identical.

## Acceptance criteria

- **AC-1** Given fixture repo `fixtures/ladder/repo` (alice: 5 GDT expansions; bob: 3 ALN expansions and 5 substantive ALN reviews; carol: 6 KRN expansions, one KRN split reverted 10 days before `--now`), reviews `fixtures/ladder/reviews.json`, when `python tools/ladder.py --repo <clone> --reviews fixtures/ladder/reviews.json --now 2026-12-01T00:00:00Z --json` runs, then eligible = {GDT: [alice], ALN: [bob]} and carol is not listed.
- **AC-2** Given the same input with `--now` 70 days after carol's revert, then carol is eligible in KRN.
- **AC-3** Given `reviews-empty-body.json` (bob's reviews approved with empty body and no inline comments), then bob is not eligible.
- **AC-4** (determinism) AC-1 run twice gives byte-identical JSON and Markdown.

## Design

- **Registry command(s):** none; repository tool `python tools/ladder.py --repo <dir> --reviews <json> --now <ISO8601> [--config <json>] [--json|--md]`.
- **Data structures:** expansions from `git log --format=%H%x00%an%x00%ae%x00%cI%x00%s`; subjects matched by `^spec\(([A-Z0-9.]+)\): (split into \d+ children|leaf|blocked on D-\d+)`; reverts matched by `^Revert "spec\(([A-Z0-9.]+)\): split`; reviews `[{pr, reviewer, state, body, inline_comments, at, node_ids[]}]`, domain from the PR's node IDs.
- **Algorithm:** aggregate counts per (domain, person) with identity normalisation by email via a config alias table; apply thresholds; sort by domain then person.
- **Errors:** `LADDER-GIT`, `LADDER-INPUT`, `LADDER-CONFIG`.
- **Determinism:** D0 given `--now`.
- **Performance budget:** under 10 s on 10 000 commits [unverified].
- **Crate:** not Rust; `tools/ladder.py`, standard library only.

## Open questions

- REQ-ECO.COMM-007 says "from repository history alone", but review data lives on the forge, not in git. This leaf takes a review export as a second input; if maintainers want history alone, reviews must be recorded as commit trailers (for example `Reviewed-by:`), which loses the "substantive" judgement.
- "Substantive review" is not defined in GOVERNANCE.md; REQ-002's default is a proposal for maintainers to confirm.
