# ECO.DATA.BENCH.BUNDLE: Release-numbers bundle generator

## Purpose

At release time, collects every benchmark record produced for the release revision and every per-format fidelity report into one generated JSON document, `release-numbers.json`, with a "generated, do not edit" header and the digest of every input. Release assembly attaches it beside the parity report; the website and docs read it. The bundle adds no numbers of its own: it copies records and reports verbatim and indexes them.

## Scope

**In:**
- `cargo xtask bench bundle --release <tag> --revision <hash> --history <dir> --fidelity <dir> --out <dir>`
- Schema `release-numbers.json` v1
- A matching drift-check entry: the header format is the same as the parity reports', so ECO.PARITY.DRIFT can regenerate and compare it

**Out:**
- Producing records (owned by `ECO.DATA.BENCH.RUN`) and fidelity reports (owned by `IO.CORP.GATE`)
- Regression flags in release notes (owned by `PLAT.HW.RUN`)
- Attaching to the release (owned by `ECO.REL`)

## Requirements

- **REQ-ECO.DATA.BENCH.BUNDLE-001** The bundle shall contain every history record whose `revision` equals the release revision (including `not-run` records) and every fidelity report in the fidelity directory, each copied unchanged with its source path and SHA-256.
- **REQ-ECO.DATA.BENCH.BUNDLE-002** The bundle shall start with a header holding the text "Generated by fid-xtask bench bundle. Do not edit.", the release tag, the revision and the SHA-256 of every input file, and no timestamp.
- **REQ-ECO.DATA.BENCH.BUNDLE-003** If no record exists for the release revision, then the bundle shall still be written, with an empty `benchmarks` list and the note `no-benchmark-records`, so a missing run is visible instead of silent.
- **REQ-ECO.DATA.BENCH.BUNDLE-004** If an input record or fidelity report is not valid JSON or has an unknown schema version, then the generator shall exit 1 with `BUNDLE-INPUT` naming the file and write nothing.
- **REQ-ECO.DATA.BENCH.BUNDLE-005** Given the same inputs, the generator shall produce byte-identical output on every supported OS.

## Acceptance criteria

- **AC-1** Given `fixtures/bundle/history/` (three records for revision `aaaa…`, one for `bbbb…`) and `fixtures/bundle/fidelity/` (two format reports), when `cargo xtask bench bundle --release v0.2.0 --revision aaaa… --history fixtures/bundle/history --fidelity fixtures/bundle/fidelity --out <tmp>` runs, then `release-numbers.json` lists three benchmarks and two fidelity reports and matches `fixtures/bundle/release-numbers.golden.json` byte for byte.
- **AC-2** Given revision `cccc…` with no records, then the bundle has an empty `benchmarks` list and note `no-benchmark-records`, exit 0.
- **AC-3** (error path) Given a truncated record file, then exit 1 with `BUNDLE-INPUT` and no output file.
- **AC-4** (drift) Changing one number in the AC-1 output by hand makes the regeneration comparison of ECO.PARITY.DRIFT (run with this generator) fail.
- **AC-5** (determinism) AC-1 produces identical bytes on Windows, Linux and macOS.

## Design

- **Registry command(s):** none; repository tool. `side_effect: W1`: writes one file into a local output root.
- **Data structures:** `{header: {text, release, revision, inputs: {<path>: sha256}}, benchmarks: [<bench-record>...], fidelity: [{path, sha256, report}], notes: [...]}`; arrays sorted by path; RFC 8785 canonical JSON.
- **Algorithm:** enumerate inputs in sorted path order; filter records by revision; validate schema versions; build and serialise canonically; atomic write.
- **Errors:** `BUNDLE-INPUT`, `BUNDLE-IO`.
- **Determinism:** D0.
- **Performance budget:** under 2 s for 1 000 records [unverified until measured].
- **Crate:** `fid-xtask` (module `bench`).
