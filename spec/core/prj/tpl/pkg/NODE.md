# CORE.PRJ.TPL.PKG: Template package format, digest, integrity and listing

## Purpose

Defines the template package: a read-only, content-addressed bundle of a project's plan, element definitions, groups, tags, metadata and project-scope settings, without measured data, stage data or journal history. The template ID is the SHA-256 of its canonical manifest, so the same content always has the same ID. This leaf owns the format, the loader with integrity checks, and listing templates in approved import roots.

## Scope

**In:** `template.json` manifest (schema version 1) in RFC 8785 form plus blob files named by digest; template digest; `Template::load` with integrity verification; `project.list_templates@1` over approved import roots.
**Out:** stripping a project into a template (`CORE.PRJ.TPL.SAVE`); instantiating a project (`CORE.PRJ.TPL.CREATE`); sharing through a marketplace (`ECO`); industry-pack templates (`IND`).

## Requirements

- **REQ-CORE.PRJ.TPL.PKG-001** A template package shall consist of `template.json` (schema version 1) in RFC 8785 canonical form and blob files each named by its SHA-256 digest, with no other files.
- **REQ-CORE.PRJ.TPL.PKG-002** The template ID shall be `sha256:` plus the hex SHA-256 of the canonical `template.json` bytes.
- **REQ-CORE.PRJ.TPL.PKG-003** When a template is loaded, the loader shall recompute the manifest digest and every blob digest, and if any differs or a listed blob is missing or an unlisted file is present, then it shall return `integrity` naming the first failing item.
- **REQ-CORE.PRJ.TPL.PKG-004** If `template.json` exceeds 64 MiB or fails its schema, then the loader shall return `validation` without reading blobs.
- **REQ-CORE.PRJ.TPL.PKG-005** When `project.list_templates@1` runs, the system shall return, for each package found in approved import roots, its handle, ID, label and creation time, sorted by label then ID, marking packages that fail integrity as `invalid`.

## Acceptance criteria

- **AC-1** Given fixture `fixtures/core/prj/tpl/pkg/good` (a template with 3 blobs), when loaded, then it succeeds and its ID equals `expected_id.txt`.
- **AC-2** (error path) Given fixtures `bad_blob` (one byte changed), `missing_blob` and `extra_file`, then each load returns `integrity` naming the item.
- **AC-3** Given an import root containing `good` and `bad_blob`, when `fid project list-templates --json` runs, then both are listed and `bad_blob` is `invalid`.
- **AC-4** (error path) Given a 65 MiB manifest, then `validation`.

## Design

- **Registry command(s):** `project.list_templates@1` R0; params `{ root?: RootId }`; result `{ templates: [TemplateSummary] }`.
- **Data structures:** `TemplateManifest { schema_version, label: Untrusted<String>, created, source_project_digest, plan, elements: [ElementDef], groups, tags, metadata, settings, blobs: [Digest] }`; `Template { id, manifest, root_handle }`.
- **Algorithm:** canonicalise with `fid-canon`; verify every blob by streaming SHA-256; directory listing through the bus file policy's resolved paths only.
- **Errors:** `integrity`, `validation`, `not_found`.
- **Determinism:** D0.
- **Performance budget:** verify a 100 MiB template in < 1 s [unverified until measured].
- **Crate:** `fid-project` (module `template_pkg`).
