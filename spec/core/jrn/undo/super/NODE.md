# CORE.JRN.UNDO.SUPER: Supersession of released records

## Purpose

A released record is never undone; it is superseded. `journal.supersede_record@1` records that a new released record replaces an old one, citing the old and new record digests and a reason, and leaves the original visible. It is W3, so only a human performs it; agents can only request it.

## Scope

**In:** `journal.supersede_record@1` (W3); the supersession event; the "superseded by" lookup used by readers and the verifier.
**Out:** producing the new record (its owning domain's W3 command); human assertions (`TRUST`); undo barriers (`CORE.JRN.UNDO.MOVE`).

## Requirements

- **REQ-CORE.JRN.UNDO.SUPER-001** `journal.supersede_record@1` shall be side-effect class W3 and shall record the superseded record digest, the new record digest and a commitment to a reason of 1 to 2,000 characters.
- **REQ-CORE.JRN.UNDO.SUPER-002** If either digest does not belong to a record committed by a W3 entry on the branch, or the old record is already superseded, then the command shall return `precondition` with reason `not_supersedable` and commit nothing.
- **REQ-CORE.JRN.UNDO.SUPER-003** When a record is superseded, the journal shall keep the original entry unchanged and visible, and the lookup `superseded_by(digest)` shall return the new digest and the supersession entry.

## Acceptance criteria

- **AC-1** Given fixture `fixtures/core/jrn/undo/super/two_releases` (records R1 and R2 released by W3 test commands), when a human runs `fid journal supersede-record --old <R1> --new <R2> --reason "wrong part revision" --json`, then one W3 entry is appended and `superseded_by(R1)` returns R2; R1's entry is unchanged.
- **AC-2** (error path) Given an agent over MCP, then a pending request is filed and nothing is superseded.
- **AC-3** (error path) Given an old digest that is not a released record, or one already superseded, then `precondition` / `not_supersedable`.
- **AC-4** (replay) Given the journal of AC-1, when replayed in exact mode, then the outcome is `IDENTICAL`.

## Design

- **Registry command(s):** `journal.supersede_record@1` W3, D0, `not_undoable`; params `{ old: Digest, new: Digest, reason: Untrusted<String> }`; result `{ entry }`; projection `request_only`.
- **Data structures:** event `RecordSuperseded { old, new, reason_commit }`; index `superseded_by: BTreeMap<Digest, (Digest, EntryHash)>` rebuilt from events.
- **Algorithm:** look up both digests among W3 entries' outputs; check the index; emit the event.
- **Errors:** `precondition` (`not_supersedable`), `validation`.
- **Determinism:** D0.
- **Performance budget:** < 1 ms [unverified until measured].
- **Crate:** `fid-journal` (module `supersede`).

## Open questions

- Built (2026-11-22, revised after the #413 review): planner, origin-bound fold, commit-stage check (`Supersessions::precommit`) and definition in `fid_journal::supersede`; bus handler in `fid_journal_cmd::supersede`. The fold follows REQ-CORE.RPL.RECON.FOLD-008: (a) `RecordSuperseded` only from the handler of `journal.supersede_record@1`, W3, human; the entry record carries the principal's identity commitment (kept as `by`) and the parameters commitment (the bus `EntryOrigin`'s); while the reason's opening is in the payload, `reason_commit` must open to it and the parameters commitment must be that of `{new, old, reason}` with the event's `old` and `new`; after erasure the parameters commitment is still required; (b) the event is reserved to that command in `fid_registry::RESERVED_EFFECTS`; (c) refused next to any `Request*` event, so an approved agent request never carries a supersession (the human runs the command); (d) the event carries `head`, the branch's logical head it was decided against, and the fold requires it to be the head before the entry; the commit stage's check is the fold's, a head mismatch being `conflict/head_moved`; (e) see the branch rules below; (f) refusals are fatal, except that promoted copies are skipped. Forged cases come from `fixtures/core/jrn/undo/super/make_fixtures.py`.
- Built, released records: an output digest (not the tombstone) of a W3 command entry signed by a human principal whose command added its events (adding stage `handler`, or `bus_release`, the commit stage's release protection on that human W3 entry), other than a supersession entry or a promoted copy. A W3 entry with release outputs signed by an agent, a script or any other non-human kind, or whose events the routing module added (`bus_route`), is refused as fatal.
- Built, branches (maintainer decisions, #413 review): the fold takes the entries of all branches in commit order, and every lookup is made at a head, the logical head of the branch being read, walking that head's logical ancestry. A fork created after a supersession, or a branch fast-forwarded over one, sees it; a fork created before it does not, and each branch decides its own supersessions. Promoted copies (`promoted_from`) are skipped for both indexes, not refused: a copy re-records on the target an entry whose authority is the original's on the source branch, and the promotion that made it is not the human W3 act of releasing or superseding there, so counting it would let a promotion mint releases or supersessions; skipping adds nothing to either index and so carries no authority.
- Obligation on `CORE.JRN.BR.PROMO` and its Rebaser (not met there yet; for that leaf): they shall refuse to promote or rebase a range of entries that holds a `RecordSuperseded` event. Since promoted copies are skipped, a supersession reaches another branch only through ancestry (a fork or a fast-forward), and this refusal keeps a supersession from being silently dropped on the target branch.
- Built, deviations: the event is `RecordSuperseded {head, new, old}`, not `{old, new, reason_commit}`. The reason commitment is the entry header's salted `reason_commit` (CORE.JRN.ENTRY), which the fold keeps in the index and binds to the parameters commitment; a salted commitment cannot be computed before the entry is built, and a copy in the event would undo erasure. The result is `{supersession}` (the event body), not `{entry}`: the entry hash is the commit stage's. A new record that is already superseded is refused too. REQ-003 API shape: the lookup is `Supersessions::superseded_by(at, digest)`, where `at` is the logical head of the branch being read (not `superseded_by(digest)` alone, since the answer depends on the branch's ancestry), returning `Superseded {new, entry, reason_commit, by}`; the index is per entry along ancestry, not one `BTreeMap<Digest, (Digest, EntryHash)>`; `released_records(at)` and `supersessions(at)` list a head's whole view.
- Built, obligations on the bus commit stage (not built): record the `reason` parameter as the entry's `reason`; build the entry record (principal commitment, the bus parameters commitment, reason commitment and its opening, logical parent) from the entry it commits; run `Supersessions::precommit` with that record and the call's parameters atomically with the commit (compare-and-swap on the event's `head`, `conflict/head_moved` otherwise); then fold the entry.
- Deferred ACs: AC-1 (entry write), AC-4 (exact replay), pending the commit stage / CORE.RPL. Both are met at event, precommit and fold level (planning and folding are deterministic); writing the W3 entry and the exact-mode replay of the journal need the bus commit stage and `CORE.RPL`, as for `CORE.JRN.BR.PROMO` (#366), whose leaf is marked built on the same terms.
- Whether supersession needs a human assertion like protected promotion is for `TRUST` to say; this leaf relies on the W3 class rules only.
