# CORE.JRN.CHAIN.VERIFY: Verify and list commands

## Purpose

The two read commands over the physical journal. `journal.verify_chain@1` recomputes every entry hash, checks every previous-hash link and every referenced blob digest, and checks each checkpoint against the chain, reporting the first failure or success with counts. `journal.list_entries@1` lists entry headers with filters. Both are R0: they never touch the Record Journal and appear in the Activity Log only while recording or as a program step (D-031).

## Scope

**In:** both commands, their parameters, result schemas, filters and paging; the verification algorithm; payload-optional verification (headers verify without payloads).
**Out:** signature checks on checkpoints (`TRUST.VERIFY`); entry hashing rules (`CORE.JRN.ENTRY`); the independent verifier binary (`TRUST`).

## Requirements

- **REQ-CORE.JRN.CHAIN.VERIFY-001** When `journal.verify_chain@1` runs, the journal shall recompute each entry hash, check each previous-hash link and sequence step, and check each referenced blob's digest, in sequence order.
- **REQ-CORE.JRN.CHAIN.VERIFY-002** When verification fails, the result shall name the stream, sequence and kind (`hash`, `link`, `sequence`, `blob`, `checkpoint`) of the first failure and stop.
- **REQ-CORE.JRN.CHAIN.VERIFY-003** When verification succeeds, the result shall report `ok` with the number of entries, blobs and checkpoints checked.
- **REQ-CORE.JRN.CHAIN.VERIFY-004** When a checkpoint is present, verification shall check that its head hash and count equal the chain at its sequence.
- **REQ-CORE.JRN.CHAIN.VERIFY-005** When `journal.list_entries@1` runs, the journal shall return entry headers filtered by stream, branch, sequence range, command ID and principal kind, in sequence order, at most 1,000 per page with a continuation token.
- **REQ-CORE.JRN.CHAIN.VERIFY-006** Both commands shall be side-effect class R0 and shall write nothing to the Record Journal.
- **REQ-CORE.JRN.CHAIN.VERIFY-007** When payloads have been removed, verification shall still pass for headers and blobs and shall report the number of entries without payload.

## Acceptance criteria

- **AC-1** Given fixture `fixtures/core/jrn/chain/verify/good` (500 entries, 20 blobs, 2 checkpoints), when `fid journal verify-chain --json` runs, then the result is `ok` with counts 500, 20 and 2, and the Record Journal is unchanged.
- **AC-2** (error path) Given fixtures `bad_hash`, `bad_link`, `bad_blob` and `bad_checkpoint` (one byte changed at a known sequence), when verified, then each reports the expected kind and sequence.
- **AC-3** Given `good` with all payloads removed, then the result is `ok` and reports 500 entries without payload.
- **AC-4** Given `good`, when `fid journal list-entries --branch main --command project.set_tags@1 --json` runs, then exactly the matching headers are returned in sequence order; with 2,500 matches, three pages are returned.
- **AC-5** Given a recording session active, when `fid journal verify-chain` runs, then one Activity Log record exists and the Record Journal is unchanged.

## Design

- **Registry command(s):**
  - `journal.verify_chain@1` R0, D0, long-running for large journals; params `{ stream?: StreamId, from_seq?: U64 }`; result `{ ok: bool, failure?: { stream, seq, kind }, checked: { entries, blobs, checkpoints, without_payload } }`.
  - `journal.list_entries@1` R0, D0; params `{ stream?, branch?, from_seq?, to_seq?, command?, principal_kind?, page_token? }`; result `{ headers: [EntryHeader], next?: PageToken }`.
- **Data structures:** `VerifyReport`; `PageToken` (opaque, encodes stream and next sequence).
- **Algorithm:** stream entries in sequence order with a bounded read buffer; recompute with `entry::hash`; compare links; hash each referenced blob through the store's verify call once per digest (sorted set); compare checkpoints.
- **Errors:** `not_found` (unknown stream or branch), `validation` (bad range or token), `cancelled`.
- **Determinism:** D0.
- **Performance budget:** verify 1 M entries in < 60 s excluding blob hashing [unverified until measured].
- **Crate:** `fid-journal` (module `verify`).

## Open questions

- Build: module `verify` of `fid-journal`. The verifier core (`verify_rows`, `list_rows`) is storage-free; with feature `store` it reads the project database (`verify_store`, `list_store`, `Journal::verify_chain`, `Journal::list_entries`) on a read-only open and needs no `Journal` (whose open refuses a broken chain). `command_defs()` declares both commands (R0, D0, CLI and MCP).
- Build: the result's `failure` adds `reason` (a finer cause within the five REQ-002 kinds, e.g. `hash/non_canonical`, `hash/unknown_version`, `sequence/gap`, `sequence/header_seq`, `link/genesis`, `blob/payload_mismatch`, `checkpoint/truncated`) and `checkpoint` (row id). Non-canonical header bytes and an unknown `schema_version` are kind `hash`; a dropped, reordered or swapped entry is `sequence`. The full ordered check list is pinned in the module documentation and in `fixtures/core/jrn/chain/verify/make_fixtures.py`.
- Build: a checkpoint row that fails on its own (malformed body, unknown format, foreign stream, columns differing from the body) is reported before the entry walk with `seq: null`.
- Build: a truncated tail is visible only through a checkpoint above the end (`checkpoint/truncated`) or a caller's trusted head (`VerifyOptions::trusted`, e.g. a signed checkpoint held by TRUST). A journal truncated below every checkpoint it still holds verifies; the fixture case `truncate_tail_no_checkpoint` records this.
- Build: the payload is checked when present: it must hash to its digest and reproduce every header commitment (`blob/payload_mismatch`); an absent payload file counts as `without_payload` (REQ-007), a missing payload row is a failure.
- Build: a verification failure is a successful call with `ok: false`; callers that must refuse on it (`Bus::execute`, replay, the extract adapter) use `internal/invariant_violated`. Command refusals map to catalogue v3: `not_found/unknown_stream|unknown_branch`, `validation/bad_range|bad_token|stale_token|schema|input_limit`, `cancelled/requested`, `internal/storage`. A listed row that does not verify on its own is `internal/invariant_violated`, never listed.
- Build: list pages scan at most 100,000 rows; a page can carry a token with fewer than 1,000 headers. The token binds 16 hex digits of the query digest (`stale_token` for another query). Parameters `from_seq`/`to_seq` are decimal strings, as every u64 in the journal.
- Deferred to the bus (CORE.BUS.ROUTE, CORE.BUS.PIPE.STAGE, not built): the CLI `fid journal verify-chain | list-entries` and MCP surfaces, the R0 handlers that hand the project store to these functions, and AC-5 (one Activity Log record while recording). AC-1 and AC-4 are tested at library level; the read-only property (REQ-006) is tested by comparing every table before and after.
- Performance budget (1 M entries in < 60 s) not measured.
