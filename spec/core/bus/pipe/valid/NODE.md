# CORE.BUS.PIPE.VALID: Command resolution, parameter validation and preconditions

## Purpose

The resolve, validate and precondition stages. VALID looks up `id@major` in the registry and refuses unknown, removed and (outside replay) hidden majors; validates parameters against the command's JSON Schema with the project keywords (quantity kind, unit, entity reference kind), normalising authored literals through `CORE.BUS.UNIT`; and evaluates the command's preconditions against the state view within their step bound.

## Scope

**In:** resolution and lifecycle checks; JSON Schema 2020-12 validation with `x-quantity`, `x-unit`, `x-ref`, `x-selector`; reference existence and kind checks through the state view; literal normalisation calls; precondition evaluation with the step bound; error JSON pointers.
**Out:** the schema vocabulary, quantity catalogue and precondition language (`CORE.REG.DEF`); lifecycle states (`CORE.REG.VER`); literal arithmetic (`CORE.BUS.UNIT`); authorisation (`CORE.BUS.POL.*`).

## Requirements

- **REQ-CORE.BUS.PIPE.VALID-001** If the command ID is unknown, or the major is unknown or in lifecycle state `removed`, then the bus shall return `not_found` naming the ID and major.
- **REQ-CORE.BUS.PIPE.VALID-002** If a major in lifecycle state `hidden` is invoked by any principal other than the replay engine's `system` principal, then the bus shall return `hidden_command`.
- **REQ-CORE.BUS.PIPE.VALID-003** If parameters fail the command's JSON Schema, then the bus shall return `validation` with the JSON pointer of the first failing value in document order and the failed keyword.
- **REQ-CORE.BUS.PIPE.VALID-004** If an `x-ref` parameter names an entity that does not exist in the state view or whose kind differs from the declared reference kind, then the bus shall return `validation` with reason `bad_reference`.
- **REQ-CORE.BUS.PIPE.VALID-005** When a parameter carries an authored literal, the bus shall replace it with the value normalised by `CORE.BUS.UNIT` and keep the literal for the entry.
- **REQ-CORE.BUS.PIPE.VALID-006** If a precondition evaluates false, then the bus shall return `precondition` naming the predicate.
- **REQ-CORE.BUS.PIPE.VALID-007** If a precondition evaluation exceeds its declared step bound, then the bus shall stop it and return `precondition` with reason `step_bound_exceeded`.
- **REQ-CORE.BUS.PIPE.VALID-008** If a parameter document exceeds 16 MiB or a nesting depth of 64, then the bus shall return `validation` with reason `input_limit` without parsing further.
- **REQ-CORE.BUS.PIPE.VALID-009** When an `agent` principal (every MCP channel derives one) invokes a command, the bus shall resolve it as if every major whose MCP projection is `never` were absent, before any lifecycle check: a name with no major the agent can see shall be `not_found` / `unknown_command`, and a hidden major of a name with a visible major `not_found` / `unknown_major`, each byte for byte the refusal of a name or major the table does not hold, so no later stage (schema, references, preconditions) runs against a hidden command for an agent (D-035).

## Acceptance criteria

- **AC-1** Given fixture `fixtures/core/bus/pipe/valid/registry.json` (commands with active, deprecated, hidden and removed majors), when `nope.cmd@1`, a removed major and an unknown major are invoked, then each returns `not_found`.
- **AC-2** (error path) Given a hidden major, when invoked by a human principal, then `hidden_command`; when invoked by the replay `system` principal, then it proceeds to validation.
- **AC-3** Given fixture `fixtures/core/bus/pipe/valid/params.jsonl` (at least 60 parameter documents with expected outcomes and JSON pointers), when validated, then every outcome and pointer matches.
- **AC-4** (error path) Given an `x-ref` to a missing entity and one to an entity of the wrong kind, then both return `validation` / `bad_reference`.
- **AC-5** Given `{"value":"10.1","unit":"mm"}` for a length parameter, when validated, then the handler receives the SI value and the entry keeps the literal.
- **AC-6** (error path) Given a precondition that is false and one that loops past its step bound, then both return `precondition`, the second with `step_bound_exceeded`, and nothing is journaled.
- **AC-7** (error path) Given a 17 MiB parameter document, then `validation` / `input_limit`.
- **AC-8** (error path, D-035) Given commands whose every major is hidden (declared `never`, no `mcp` surface, removed, lifecycle-hidden) and a name with one visible and two hidden majors, when an agent resolves each hidden major, a missing major and a missing name, with any parameters, then every refusal is byte for byte (RFC 8785 JSON) the one the agent gets from a table without the hidden majors; a human still resolves them as before.

## Design

- **Registry command(s):** none; pipeline stages.
- **Data structures:** `Resolved { def: &CommandDef, lifecycle }`; `ValidationError { pointer: JsonPointer, keyword, reason }`; compiled schema cache keyed by manifest digest.
- **Algorithm:** resolve by exact `(id, major)` lookup; compile each schema once per manifest digest; validate with an allowlisted JSON Schema 2020-12 validator plus project keyword hooks; walk `x-ref` values and query the state view; call `unit::normalise` on literal objects; evaluate preconditions with the registry evaluator and its step counter.
- **Errors:** `not_found` (reasons `unknown_command`, `unknown_major`, `removed_major`), `hidden_command` (`hidden_major`), `validation` (reasons `schema`, `bad_reference`, `unit_mismatch`, `literal_out_of_range`, `literal_syntax`, `input_limit`), `precondition` (reason `false`, `step_bound_exceeded`). All from bus error catalogue v3 (`CORE.BUS.PIPE.ERR`); this leaf adds no code or reason, and never returns `internal` for a caller's mistake.
- **Determinism:** D0; document-order traversal, no clock.
- **Performance budget:** validation of a 1 KiB parameter document in < 50 µs with a warm schema cache [unverified until measured].
- **Crate:** `fid-bus` (module `validate`).
- **Pinned choices (as built):**
  - **API for `CORE.BUS.PIPE.STAGE`:** `CommandTable::build(manifest_digest, defs, catalogue, &ContextTypes)` once per manifest (cached by digest in `TableCache`, at most 4 tables); then per call `table.resolve(id, major, &principal) -> Resolved`, `resolved.validate_json(bytes, view)` or `validate_value(&CValue, view) -> Validated` (refusal `ValidationError { pointer, keyword, reason }`, `Into<BusError>`), `resolved.check_preconditions(validated.params(), roots)`. Free-function forms `resolve`, `validate_params`, `validate_params_json`, `check_preconditions` return `BusError`. `Validated` gives the handler's `ValidParams` (SI values), the entry's arguments as entered (`entry_params`), each literal with its pointer and SI bits (`literals`), and the entry's algorithm IDs (`core.unit.normalise@1.0.0` when a literal was normalised).
  - **Resolution:** exact `(id, major)`; an ID that is not a valid command name or not in the table is `unknown_command`; a known ID without that major `unknown_major`; `removed` `removed_major`. `active` and `deprecated` majors resolve (`deprecated` → `active` is a legal transition and the deprecation window of `CORE.REG.VER.LIFE` exists so callers can keep calling); `Resolved::deprecation()` gives `replaced_by` and `remove_after` for the surface. `hidden` resolves only for the replay engine's `system` principal: kind `system` and principal ID `replay` (`REPLAY_PRINCIPAL_ID`); a `system` principal comes only from the internal channel (`CORE.BUS.PRIN`).
  - **Validator:** written for the bus (no new JSON Schema crate: the vetted Rust validators pull a backtracking regex engine or a large dependency tree), compiled once per schema. Every keyword of the `CORE.REG.DEF.SCHEMA` vocabulary is asserted, applied, or an annotation that 2020-12 itself never asserts (`title`, `description`, `default`, `examples`, `deprecated`, `readOnly`, `writeOnly`, `$comment`, `$anchor`, `$dynamicAnchor`, `$vocabulary`, `content*`, and the project annotations `x-unit`, `x-ui`, `x-untrusted`, `x-standards-ref`, `path_like`, `x-extensions`, which later stages read). Asserted: `type`, `const`, `enum`, `multipleOf` (exact decimal arithmetic on the shortest round-trip form of each number, so `0.3` is a multiple of `0.1`), `maximum`, `exclusiveMaximum`, `minimum`, `exclusiveMinimum`, `maxLength`, `minLength` (Unicode scalar values), `pattern`, `format`, `maxItems`, `minItems`, `uniqueItems`, `contains`/`minContains`/`maxContains`, `maxProperties`, `minProperties`, `required`, `dependentRequired`; applied: `$ref` (`#` and `#/<pointer>` landing on a schema position), `$defs`, `allOf`, `anyOf`, `oneOf`, `not`, `if`/`then`/`else`, `dependentSchemas`, `propertyNames`, `prefixItems`, `items`, `properties`, `patternProperties`, `additionalProperties`, `unevaluatedItems`, `unevaluatedProperties` (with 2020-12 annotation collection; they run only when every other keyword of their schema object passed). Anything else fails compilation (unknown keyword, `$dynamicRef`, `$schema` other than 2020-12 or below the root, `$id` below the root, the array form of `items`, a format the bus does not assert, a pattern outside the subset) and the command then refuses every call with `validation`/`schema`, keyword `schema` (fail closed).
  - **First failure in document order:** document order is that of the RFC 8785 canonical form (members by UTF-16 code units, then array index; a value before everything inside it). Each keyword reports its first failure; a schema reports the earliest by (pointer, keyword rank), first evaluated winning a tie. Rank: `json`, `input_limit`, `false`, `x-quantity`, `type`, `const`, `enum`, `multipleOf`, `maximum`, `exclusiveMaximum`, `minimum`, `exclusiveMinimum`, `maxLength`, `minLength`, `pattern`, `format`, `x-ref`, `x-selector`, `maxItems`, `minItems`, `uniqueItems`, `contains`, `minContains`, `maxContains`, `maxProperties`, `minProperties`, `required`, `dependentRequired`, `$ref`, `allOf`, `anyOf`, `oneOf`, `not`, `if`, `then`, `else`, `dependentSchemas`, `propertyNames`, `prefixItems`, `items`, `properties`, `patternProperties`, `additionalProperties`, `unevaluatedItems`, `unevaluatedProperties`, `schema`. Reported at the instance itself: the assertions, `anyOf`, `oneOf`, `not`, `contains`, `required` (the object that lacks the member), `dependentRequired`, `uniqueItems`; passed up unchanged: a subschema's own failure under `$ref`, `allOf`, `then`, `else`, `dependentSchemas` and the child applicators; a `false` subschema fails under the keyword that applied it; `propertyNames` fails at the member it rejects. Pseudo-keywords: `json` (not acceptable JSON: syntax, duplicate key, invalid UTF-8, non-finite number), `input_limit`, `schema`.
  - **Patterns (`pattern`, `patternProperties`, `format: regex`):** an allowlisted ECMA-262 subset (literals, `.`, `^`, `$`, groups incl. `(?:)` and `(?<name>)`, `|`, greedy and lazy quantifiers, classes with ranges `a-z` between two single characters and a literal `-` first, last, after a range or escaped, `\d \D \w \W \s \S`, `\t \n \v \f \r \0 \xHH \uHHHH`, escaped syntax characters, `\b` in classes) translated with ECMA meanings spelled out (`\d` = `[0-9]`, `\w` ASCII, `\s` ECMA WhiteSpace and LineTerminator, `.` excludes LF, CR, U+2028, U+2029, `$` the end of input, unanchored search) and compiled with the `regex` crate (MIT OR Apache-2.0, already in the lock and through cargo-deny). The crate is built with `std` and `unicode` only, so its DFA features are off and every match runs on its PikeVM: an NFA simulation in time O(input length x program size), no backtracking. Each pattern's program size is measured when the schema is compiled (the smallest power-of-two size limit from 1 KiB up that it compiles under) and every match is charged one step per KiB of input (at least one) times that size in KiB. Limits: pattern 1,024 bytes, compiled size 1 MiB, nesting 32 (the lazy-DFA limit is set but inert). Refused: lookaround, backreferences, `\b \B` outside classes, `\p`, `\c`, `\k`, inline flags, `[]` and `[^]` (so also `]` first in a class), a `-` next to another `-` in a class (`[--a]`, `[a--]`, `[^--/]`) or between a class escape and anything (`[\d-z]`, `[a-\d]`) (maintainer decision in the re-review of #341; a `-` first, last or directly after a range is a literal hyphen, as in ECMA-262: `[a-z0-9_-]`, `[-a]`, `[\w-]`, `[a-z-0]`), a range out of order, a lone `{`, `}` or `]`, octal and other escapes.
  - **Formats asserted** (strings only; other types pass): `date`, `time`, `date-time` (RFC 3339 §5.6, offset required in `time`, `T`/`Z` either case, day valid for the month, second 60 only at 23:59 UTC), `duration` (RFC 3339 Appendix A), `uuid` (RFC 4122 hyphenated, either case), `ipv4` (dotted quad, no leading zeros), `ipv6` (RFC 4291 §2.2, no zone, no brackets), `hostname` (RFC 1123, at most 253 characters, no trailing dot), `json-pointer` (RFC 6901), `regex` (the subset above). Any other format name fails compilation.
  - **Limits:** document 16 MiB (text length, or canonical length of a parsed value), depth 64 (root container is level 1), 2^20 values and keys; each checked before parsing or walking further. Evaluation: 4,000,000 steps: one per schema application, one per object member or array element each keyword looks at (plus one per member to order an object's members), one per 1,024 bytes of string or canonical value examined, the pattern charge above, and for `format: regex` (which compiles the string) 1,024 steps plus one per byte, at most 64 such checks per document. At most 128 nested schema applications (enough for a 64-level document whose schema adds a `$ref` per level). A schema at most 64 levels and 65,536 positions. A limit reached during evaluation stops it with `input_limit`, which no `anyOf`, `oneOf`, `not` or `if` can turn into a pass. Parsed values may carry only JSON-text number forms (no `I64`, `U64`, `F64Bits`: `validation`/`schema`, keyword `type`).
  - **Stack (for `CORE.BUS.PIPE.STAGE`):** validation recurses once per nested schema application, so it needs stack in proportion to the 128-application limit: measured under 256 KiB in a release build and under 768 KiB in a debug build (the deep-recursion test runs on a 1 MiB thread). The pipeline must run validation on a thread with at least 1 MiB of stack; the default Rust thread (2 MiB) and the main thread on Linux, macOS and Windows (1 MiB or more) all qualify.
  - **Integers beyond 2^53 (fail closed; maintainer decision in the review of #341):** the text entry point refuses a number token whose value is an integer of magnitude above 2^53 that no binary64 number equals (`9007199254740993`, `1e23`), with `validation`/`schema`, keyword `json`, at the first such value in document order. Exactly representable ones (`9007199254740994`, `1e20`) and numbers with a fractional part pass. The scan is charged against 20,000,000 limb operations, beyond which it is `input_limit`. A parsed value has already been rounded, so callers holding JSON text use `validate_json`.
  - **Authored literals:** where a schema object holds `x-quantity` and the instance is an object, the object is a literal: `unit::normalise_value` with that kind, its refusal reasons kept (`literal_syntax` for a wrong shape or grammar, `unit_mismatch`, `literal_out_of_range`) at the literal's pointer under keyword `x-quantity`; the schema object's other keywords then see the SI number (so `minimum: 0` refuses `-1 mm`). Literals are kept only from passing paths; one literal normalised to two different values is `schema`. A broken invariant inside the unit module is returned as it is (`internal/invariant_violated`, never a caller refusal). Compile-time rule (maintainer decision in the re-review of #341): a numeric keyword (`minimum`, `maximum`, `exclusiveMinimum`, `exclusiveMaximum`, `multipleOf`) is accepted only in a schema object that has its own `x-quantity` or its own `type` excluding `object`; anywhere else (an applicator, a child schema reached through `properties`, `patternProperties`, `prefixItems` or `then`, a `$defs` entry) it could meet an authored literal it would silently ignore, so the schema is refused. `x-quantity` reachable in place from a `contains` or `not` subschema is refused too, since those never keep what their subschema normalised. An `x-quantity` schema carries its own numeric bounds.
  - **References:** `x-ref` (or `x-selector` alone) on a string: a valid `EntityId` that exists in the state view; with `x-ref` its kind equals the declared type or starts with the type and a dot (`feature.plane` is a `feature`, `featurex` is not); `x-selector: list` takes an array of such strings, the first bad element reported. Otherwise `bad_reference` (a non-string is `schema`).
  - **Preconditions:** compiled at table build with `fid_registry::compile_command`; `params.*` read from the validated (SI) parameters typed by the parameter schema; other roots from the caller's `PredContext` (`NoRoots` when none). False, or an evaluation error, is `precondition`/`false`; the evaluator's budget stop is `step_bound_exceeded`; a precondition that does not compile refuses every call (`false`).

## Open questions

- The step bound per precondition comes from `CORE.REG.DEF` (at most 10,000 steps [unverified that this suffices]). `CORE.REG.DEF.FIELD` accepts bounds up to 1,000,000 (`MAX_PRECONDITION_BOUND`) while `CORE.REG.DEF.PRED` caps them at 10,000 (`fpl_bound`); a definition above 10,000 does not compile here and its command refuses every call. Needs a decision in `CORE.REG.DEF`.
- Needs `CORE.BUS.PRIN` (or `CORE.RPL`) to pin the replay engine's principal subject ID; this leaf uses `replay`.
- Needs `CORE.REG.DEF.SCHEMA` to refuse at registry build what this validator refuses at compile time (formats outside the asserted list, patterns outside the ECMA-262 subset), so no command can be registered that the bus will refuse on every call; and to pin the `x-ref` kind rule (`type` or `type.` prefix) next to the entity kinds.
- `CORE.BUS.PIPE.STAGE` must validate the parameter text with `validate_json` (`validate_params_json`), never a pre-parsed value: only the text entry point refuses integers above 2^53 that no binary64 number equals, and it applies the size and depth limits before parsing. The `Invocation.params` of STAGE needs to carry the JSON text (or the bytes it was parsed from) for this.
- `CORE.BUS.PIPE.STAGE` should record `Validated::entry_params()`, the literals and `Validated::algorithms()` in the entry, and show `Resolved::deprecation()` on the surfaces.
- An assignment asked for deprecated majors to be refused. This leaf keeps REQ-001: deprecated majors resolve (with a notice); only unknown, removed and (outside replay) hidden majors are refused. Refusing deprecated majors would need a requirement change here and in `CORE.REG.VER.LIFE`, and a catalogue reason.
- Performance budget (1 KiB document under 50 µs warm) not yet measured; the step budget bounds the worst case.

## Change log

- 2026-11-21 (security fix for D-035, maintainer decision): `CommandTable::resolve` did not know its audience, so an agent asking for `id@N` of a hidden name got `unknown_major` (or `removed_major` / `hidden_command`) and learned the name exists. New REQ-009 and AC-8: for an `agent` principal a `never`-projected major does not exist and is checked first; the refusals equal those for a real miss, and since validation needs a resolved command, a hidden command's schema is never used for an agent. The `unknown_major` detail names only the requested major, so it lists no major at all, visible or hidden. No REQ ID was renumbered.
