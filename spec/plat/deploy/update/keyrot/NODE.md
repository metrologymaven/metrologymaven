# PLAT.DEPLOY.UPDATE.KEYROT: Key transitions

## Purpose

Decides, offline, which release keys an installed version trusts: the keys bundled with it, plus any new key reached through a chain of key-transition statements each signed by an already-trusted key. This is how a site that skipped several releases can still accept a bundle signed after a key rotation.

## Scope

**In:**
- Loading the bundled release public keys of the installed version
- Parsing key-transition statements (DSSE, payload type `application/vnd.fid.key-transition+json`, fields `old_keyid`, `new_keyid`, `class`, `effective_from_version`, `published_at`, as published by `ECO.REL.SIGN.GUIDE`)
- Building the trusted set by repeated extension until no statement adds a key

**Out** (and which node owns it instead):
- Producing and publishing statements (`ECO.REL.SIGN.GUIDE`, `ECO.REL.SIGN.CUSTODY`)
- Verifying bundles (`PLAT.DEPLOY.UPDATE.VERIFY`)

## Requirements

- **REQ-PLAT.DEPLOY.UPDATE.KEYROT-001** The trusted set shall start with the release-class public keys bundled with the installed version and shall exclude nightly-class keys.
- **REQ-PLAT.DEPLOY.UPDATE.KEYROT-002** A transition statement shall add `new_keyid` only if its DSSE signature verifies against `old_keyid`, `old_keyid` is already trusted, and `class` is `release`.
- **REQ-PLAT.DEPLOY.UPDATE.KEYROT-003** A key added by a transition shall be trusted only for bundles whose version is at least `effective_from_version`.
- **REQ-PLAT.DEPLOY.UPDATE.KEYROT-004** Extension shall iterate until no new key is added, bounded at 64 statements, and the result shall not depend on the order in which statements are supplied.
- **REQ-PLAT.DEPLOY.UPDATE.KEYROT-005** The module shall use no network and no clock; `published_at` is reported but not checked.

## Acceptance criteria

- **AC-1** Given bundled key A and statements A→B and B→C (fixtures `fixtures/plat/deploy/update/keys/`), when the set is built, then it is {A, B, C} with C trusted from its `effective_from_version`.
- **AC-2** Given the same statements in reverse order, then the set is identical.
- **AC-3** (error path) Given a statement A→D signed by D, then D is not added and the statement is reported `untrusted_signer`.
- **AC-4** (error path) Given a nightly-class statement A→N, then N is not added (`wrong_class`).
- **AC-5** (bounds) Given 65 statements, then `TooManyTransitions` and no panic.

## Design

- **Registry command(s):** none; module `keys` of `fid-update-offline`.
- **Data structures:** `KeySet { keys: BTreeMap<KeyId, TrustedKey { key, from_version: Option<Version>, via: Vec<KeyId> }> }`; `TransitionReport { statement_digest, outcome }`.
- **Algorithm:** fixed-point loop over statements sorted by digest.
- **Errors:** `TooManyTransitions`, per-statement outcomes `added`, `untrusted_signer`, `wrong_class`, `malformed`.
- **Determinism:** D0.
- **Crate:** `fid-update-offline` (module `keys`).
