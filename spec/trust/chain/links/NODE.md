# TRUST.CHAIN.LINKS: Chain walk, findings and check-chain command

## Purpose

Walks the journal segment inside a package entry by entry, recomputes each hash, checks predecessor links and sequence numbers, and reports either `VALID` or `BROKEN` at the first failing entry. It also owns `verify.check_chain@1`, which composes the walk with the checkpoint check (`TRUST.CHAIN.CKPT`) and result linkage (`TRUST.CHAIN.RESLINK`) into one typed findings report.

## Scope

**In:**
- Streaming read of `journal/segment.jsonl` via the package reader
- Per-entry hash recomputation and comparison with the stored hash
- Predecessor-hash and sequence-number continuity
- Finding kinds: `HASH_MISMATCH`, `LINK_MISMATCH`, `SEQUENCE_GAP`, `SEQUENCE_REPEAT`, `TRUNCATED`
- Chain verdict `VALID | BROKEN` and the registry command composing CKPT and RESLINK
- Performance target for 1,000,000 entries

**Out:**
- Canonicalisation and entry hashing (`TRUST.CHAIN.CANON`)
- Checkpoint matching (`TRUST.CHAIN.CKPT`)
- ResultRecord linkage (`TRUST.CHAIN.RESLINK`)
- Composing with signature and replay sections (`TRUST.VERIFY.REPORT`)

## Requirements

- **REQ-TRUST.CHAIN.LINKS-001** For each entry, the walker shall recompute the entry hash with `TRUST.CHAIN.CANON` and compare it with the stored hash.
- **REQ-TRUST.CHAIN.LINKS-002** For each entry after the first, the walker shall check that its previous-hash field equals the preceding entry's hash and its sequence number is the preceding one plus one.
- **REQ-TRUST.CHAIN.LINKS-003** The walker shall report `VALID` only when every entry passes REQ-TRUST.CHAIN.LINKS-001 and -002, and otherwise `BROKEN` with the zero-based index and kind of the first failing entry.
- **REQ-TRUST.CHAIN.LINKS-004** The first entry of the segment shall be anchored to the checkpoint or session header that `TRUST.PKG.CONTENT` placed at its start; if no anchor is present, then the walker shall report finding `UNANCHORED` and the verdict `BROKEN`.
- **REQ-TRUST.CHAIN.LINKS-005** If the last line of the segment is incomplete or fails to parse, then the walker shall report `TRUNCATED` at that index.
- **REQ-TRUST.CHAIN.LINKS-006** The walker shall verify 1,000,000 entries of median header size 1 KiB in under 30 s on the reference CI machine with no network access [unverified].
- **REQ-TRUST.CHAIN.LINKS-007** `verify.check_chain@1` shall return the chain verdict, all checkpoint results and all `UNLINKED` records in one report.

## Acceptance criteria

- **AC-1** Given golden package `fixtures/pkg/golden/points.zip`, when `fid verify check-chain points.zip --json` runs, then the verdict is `VALID` with zero findings.
- **AC-2** (error path) Given `fixtures/chain/tamper/{modified,removed,inserted,reordered,truncated}.zip`, each made from AC-1 by one edit at entry 17, then each verdict is `BROKEN` with index 17 (or 16/17 for removal as documented in its `expect.json`) and the expected kind.
- **AC-3** (performance) Given the generated `fixtures/chain/large-1m.zip` (seeded), when checked in CI with networking disabled, then it completes in under 30 s.
- **AC-4** (MCP) Given AC-1 inputs as handles, when `verify_check_chain` is called, then the result equals the CLI JSON.

## Design

- **Registry command(s):** `verify.check_chain@1`, R1; params `package: PackageHandle`, `trust_root: Option<FileHandle>` (for signed checkpoints); result `ChainReport { verdict, findings: Vec<Finding>, checkpoints: Vec<CheckpointResult>, unlinked: Vec<RecordId> }`. Activity Log only when run inside `fid`.
- **Data structures:** `Finding { index: u64, kind, detail }`.
- **Algorithm:** single streaming pass, holding only the previous hash and sequence; collect entry hashes into a sorted vector for RESLINK; call CKPT for each checkpoint member.
- **Errors:** passthrough `pkg.*`, `canon.*`.
- **Determinism:** D0.
- **Performance budget:** see REQ-TRUST.CHAIN.LINKS-006.
- **Crate:** `fid-chain` (module `links`), command registered by `fid-verify`.
