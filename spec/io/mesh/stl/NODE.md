# IO.MESH.STL: STL reader and writer

## Purpose

Imports ASCII and binary STL into GEO triangle meshes and exports meshes back to both encodings. STL is the most common scan-data hand-off, so the reader must be fast and must not be fooled by binary files whose header begins with `solid`.

## Scope

**In:**
- Encoding detection by size consistency (84 + 50·n bytes) before the `solid` keyword
- Binary STL (little-endian f32, attribute byte count kept but ignored) and ASCII STL (`facet normal`, `outer loop`, `vertex`, case-insensitive keywords)
- Header text and solid names as untrusted metadata
- Export to binary and ASCII STL with a precision report
- `import.mesh_stl@1` (W2) and `export.mesh_stl@1` (W1, `fs_effect: write_root`)

**Out:**
- Vertex welding (SCAN); STL has no shared vertices, so the importer stores three vertices per face as read [see open questions]
- Units: STL declares none, so `unit` is required (`IO.REG.PROV`)

## Requirements

- **REQ-IO.MESH.STL-001** When an STL file is imported, the reader shall treat it as binary if its byte length equals 84 + 50·n for the triangle count n in bytes 80..84, and as ASCII otherwise, regardless of the leading `solid` keyword.
- **REQ-IO.MESH.STL-002** If a file is not size-consistent binary and does not parse as ASCII STL, then the import shall fail with `truncated_file` when its length is below 84 + 50·n for a plausible n, and `malformed` with a line number otherwise.
- **REQ-IO.MESH.STL-003** The reader shall store f32 coordinates widened exactly to f64 before unit conversion and shall record source precision `f32`.
- **REQ-IO.MESH.STL-004** When a mesh is exported, the writer shall produce binary STL by default and ASCII when `encoding=ascii`, and the export report shall include the f32 precision report.
- **REQ-IO.MESH.STL-005** The importer shall read a 10-million-triangle binary STL in under 5 s on the reference hardware [unverified until measured].

## Acceptance criteria

- **AC-1** Given `fixtures/io/mesh/stl/cube_bin.stl` (12 triangles, binary) and `--unit mm`, when `fid import mesh-stl --json` runs, then the report shows 12 faces, 36 vertices, source precision `f32`, unit `mm`.
- **AC-2** Given `fixtures/io/mesh/stl/cube_bin_solid_header.stl` (binary with header `solid cube`), then the result equals AC-1.
- **AC-3** Given `fixtures/io/mesh/stl/cube_ascii.stl`, then 12 faces are imported with coordinates equal to AC-1's.
- **AC-4** (error path) Given `fixtures/io/mesh/stl/cube_bin_truncated.stl` (last 20 bytes removed), then the import fails `truncated_file` and journals nothing.
- **AC-5** (error path) Given `fixtures/io/mesh/stl/bad_vertex.stl` (ASCII with `vertex 1 2`), then it fails `malformed{line: 4}`.
- **AC-6** Given the mesh from AC-1, when exported to binary STL and re-imported, then all coordinates are bit-identical.
- **AC-7** Given a seeded 10^7-triangle binary STL generated at test time, when imported on reference hardware, then wall time < 5 s (benchmark, not a unit test gate until hardware is fixed).
- **AC-8** (replay) Given the journal of AC-1 and the same source file, when replayed exactly, then the outcome is `IDENTICAL`.

## Design

- **Registry commands:** `import.mesh_stl@1` (W2; params: `source` handle, `unit`, `stage?`, `dry_run?`; result `ImportReport`), `export.mesh_stl@1` (W1, `fs_effect: write_root`; params: `mesh` ref, `target` handle, `encoding: binary|ascii`, `overwrite?`; result `ExportReport`). The leaf's `side_effect` names its strongest class (W2).
- **Data structures:** none new beyond `MeshBuilder` inputs.
- **Algorithm:** binary path reads 50-byte records in 64 KiB chunks; ASCII path is a line tokenizer with bounded line length (4 KiB). ASCII writer uses shortest round-trip f32 formatting.
- **Errors:** `truncated_file`, `malformed`, `unit_required`, `limit_exceeded`.
- **Determinism:** D0.
- **Performance budget:** REQ-005.
- **Crate:** `fid-io-mesh`.
